# Data Transformation

**Focus:** Flatten event payloads into analytics-ready tables using ETL pipelines.

## Scenario

Chama is a modern company with iOS and Android apps. To grow the company, Chama needs to collect information about app usage and make it available throughout the organization.

Some information is generated by the apps and the backend API. Other sources, such as the Google Play Store, can provide useful insights into app performance and user ratings. Chama is data-oriented, and most decisions are based on appropriate metrics. Data quality is therefore a shared responsibility and a key requirement.

## Task 2: Design a Medallion Architecture

Using the Chama scenario and the event data from Task 1, design an ingestion and analytics solution based on the **Bronze**, **Silver**, and **Gold** medallion layers.

### Requirements

- **Bronze:** Store the raw event JSON and raw app-store data without changing the source values. Describe the folder or table layout, partitioning approach, and retention of the original data.
- **Silver:** Parse and normalize the event payloads into validated tables, including the three outputs from Task 1. Explain how you would handle malformed payloads, duplicate events, missing fields, late-arriving data, and schema changes.
- **Gold:** Define one or two analytics-ready tables or views for business users. Examples include daily offer performance, dealer pricing summaries, or app-store rating trends. List the metrics and dimensions each output would contain.
- **Pipeline operations:** Describe how the pipeline would be scheduled, retried, monitored, and made idempotent so that rerunning a load does not create duplicate data.
- **Data quality:** Define checks for completeness, uniqueness, valid data types, valid price ranges, timestamp conversion, and freshness. Explain where failed records and quality results would be stored.

### Deliverables

1. A simple architecture diagram showing sources, pipeline steps, medallion layers, and consumers.
2. A short description of the tables or files in each layer, including their grain and key columns.
3. Pseudocode, SQL, or code snippets for the main transformations and at least three data-quality checks.
4. A brief explanation of design assumptions, trade-offs, and how the solution could scale as event volume grows.

## Practicalities

- Use the programming language and tools you are most comfortable with.
- Keep the solution readable and organized.
- Include the three generated CSV files and the source code used to create them.
- Document important assumptions and edge cases.
- The structure of the code and the clarity of your reasoning are more important than the final CSV files alone.
